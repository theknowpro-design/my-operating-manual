# My Operating Manual - Versioning

## Overview

The versioning system tracks the state of the My Operating Manual application across three dimensions:

1. **App Version** — My Operating Manual application release
2. **PDF Engine Version** — PDF generation engine release
3. **Pipeline Version** — Interview pipeline version

Every generated PDF includes version metadata for tracking, debugging, and auditing.

## Version File

### Location

`modules/pdf-engine/version.json`

### Structure

```json
{
  "pdfEngineVersion": "1.0.0",
  "pipelineVersion": "1.0.0",
  "appVersion": "1.0.0",
  "buildTimestamp": "2026-08-12T05:10:00Z",
  "systemName": "My Operating Manual",
  "description": "Operating Manual PDF generation system - locked architecture for single-purpose PDF exports"
}
```

### Fields

| Field | Type | Purpose | Example |
|-------|------|---------|---------|
| `appVersion` | string | App release version | `"1.0.0"` |
| `pdfEngineVersion` | string | PDF engine release | `"1.0.0"` |
| `pipelineVersion` | string | Pipeline version | `"1.0.0"` |
| `buildTimestamp` | ISO 8601 | When version was built | `"2026-08-12T05:10:00Z"` |
| `systemName` | string | System identifier | `"My Operating Manual"` |
| `description` | string | System description | `"Operating Manual PDF generation system..."` |

## Semantic Versioning

All three version numbers follow [Semantic Versioning](https://semver.org/):

```
MAJOR.MINOR.PATCH
X.Y.Z

MAJOR: Breaking changes, incompatibilities
MINOR: New features, backward compatible
PATCH: Bug fixes, patches, backward compatible
```

### Version Rules

**MAJOR Increment When:**
- Changing interview questions (phase structure)
- Changing PDF output format (non-backward-compatible)
- Changing locked options (breaking compatibility)

**MINOR Increment When:**
- Adding new interview phases
- Adding new optional questions
- Adding new approved assets
- Adding new PDF features (backward compatible)
- Adding new validation rules

**PATCH Increment When:**
- Bug fixes
- Error message improvements
- Performance improvements
- Non-user-facing changes

### Current Versions

All three versions are currently **1.0.0** (initial release):
- App, pipeline, and PDF engine launched together
- First stable production version

## Build Timestamp

### What It Records

The `buildTimestamp` records when the version.json file was last updated (build time).

**Format:** ISO 8601 UTC timestamp  
**Example:** `"2026-08-12T05:10:00Z"`  
**Usage:** Historical tracking, audit trails

### How to Update

Manually edit `modules/pdf-engine/version.json`:

```bash
# Before commit, update timestamp to current UTC time
# Use format: YYYY-MM-DDTHH:MM:SSZ

# Example:
# "buildTimestamp": "2026-08-12T18:30:45Z"
```

Or use date command:

```bash
# On Unix/Linux/macOS:
date -u +'%Y-%m-%dT%H:%M:%SZ'

# On Windows PowerShell:
[System.DateTime]::UtcNow.ToString('yyyy-MM-ddTHH:mm:ssZ')
```

### Update on Release

When releasing a new version:

1. Update version numbers
2. Update buildTimestamp to current UTC time
3. Commit with version bump message
4. Tag release with version

Example:
```bash
# Edit version.json
{
  "pdfEngineVersion": "1.0.1",
  "pipelineVersion": "1.0.1",
  "appVersion": "1.0.1",
  "buildTimestamp": "2026-08-12T18:30:45Z",  # ← Updated
  # ...
}

# Commit
git add modules/pdf-engine/version.json
git commit -m "Release v1.0.1"
git tag v1.0.1
```

**Visible in:**
- PDF reader properties dialog

### Version Helper

**File:** `modules/pdf-engine/utils/versionHelper.js`

**Functions:**
- `getVersionWithTimestamp()` — Load version.json + current timestamp
- `formatVersionHtmlComment()` — Create HTML comment string
- `getVersionMetadata()` — Get structured version object

**Usage:**

```javascript
import { getVersionWithTimestamp } from './utils/versionHelper.js'

const versionInfo = getVersionWithTimestamp()
// Returns:
// {
//   appVersion: '1.0.0',
//   pdfEngineVersion: '1.0.0',
//   pipelineVersion: '1.0.0',
//   buildTimestamp: '2026-08-12T05:10:00Z',
//   generatedAt: '2026-08-12T18:30:45Z',  ← Real-time generation
// }
```

## Generation Timestamp vs Build Timestamp

### Distinction

| Aspect | Build Timestamp | Generated Timestamp |
|--------|-----------------|-------------------|
| **When** | When version.json was last built/released | When PDF is actually created |
| **Type** | Static, stored in version.json | Dynamic, calculated at PDF generation |
| **Updates** | Manual, on release | Automatic, on every PDF export |
| **Precision** | Seconds | Milliseconds (if captured) |
| **Purpose** | Track releases | Track PDF creation |
| **Example** | `2026-08-12T05:10:00Z` (release day) | `2026-08-12T18:30:45Z` (PDF export time) |

### Why Both?

**Build Timestamp:**
- Answers: "What version was deployed?"
- Stable across all PDFs from same build
- Useful for QA/deployment tracking

**Generated Timestamp:**
- Answers: "When was THIS PDF created?"
- Unique per PDF export
- Useful for audit trails
- Shows when user downloaded PDF

## Version Propagation

### Data Flow

```
version.json (source of truth)
    ↓
getVersionWithTimestamp()
    ├─→ Load version.json
    ├─→ Add generatedAt (current time)
    ├─→ Return combined object
    
    ↓
formatVersionHtmlComment()
    ├─→ Create HTML comments
    └─→ Inject into <article> element

    ↓
generateOperatingManualPdf()
    ├─→ Embed HTML comments
    ├─→ Add to PDF metadata
    └─→ Save with PDF file

    ↓
PDF File (with embedded version info)
    ├─→ HTML comments (visible in source)
    └─→ PDF metadata (visible in properties)
```

### Check Deployed Version

View version.json:

```bash

```

### Check PDF Version

**In Browser Developer Tools:**

```javascript
// Inspect HTML source to see comments

// Look for: <!-- Generated by My Operating Manual v... -->
```

**In PDF Reader:**

```

Look for: appVersion, pdfEngineVersion, generatedAtUtc
```

**Command Line (if pdfinfo available):**


## Version Compatibility

### Current State (v1.0.0)

All three versions are synchronized:
- App: 1.0.0
- PDF Engine: 1.0.0
- Pipeline: 1.0.0

### Future Decoupling

Versions *can* diverge if needed:

**Scenario:** PDF engine improvements but interview unchanged

```json
{
  "appVersion": "1.0.0",         // Unchanged
  "pipelineVersion": "1.0.0",    // Unchanged
  "pdfEngineVersion": "1.0.1",   // Bumped for bug fix
  "buildTimestamp": "2026-08-12T18:30:45Z"
}
```

This indicates:
- Interview questions are same (pipeline 1.0.0)
- UI/UX is same (app 1.0.0)
- PDFs are slightly improved (engine 1.0.1)

### Compatibility Notes

Currently:
- All three versions are locked together (single release)
- Breaking changes to any increment MAJOR version for all
- New features increment MINOR for all

Could change:
- Decouple versions for independent releases
- Track each component's version separately
- More granular compatibility tracking

## Tracking PDFs

### Use Case: Audit Trail

Every PDF file includes:
1. Author (from interview)
2. Generated timestamp (when created)
3. App version (which version of app created it)
4. Build timestamp (which build was used)

**Question:** "What version generated this PDF?"  
**Answer:** Check PDF properties → Custom properties → `appVersion`

**Question:** "When was this PDF created?"  
**Answer:** Check PDF properties → Custom properties → `generatedAtUtc`

### Use Case: Debugging

If user reports issue:
1. Ask user to export PDF
2. Check PDF properties
3. See app/engine/pipeline versions
4. Reproduce with exact same versions
